# Решения по качеству

Что сломалось, почему, что исправили и цифры до/после. Метрика разбора — доля
полностью верных `SearchFilters` на dev (20 кейсов), каждая конфигурация гоняется
×3; указаны среднее ± стандартное отклонение по повторам. Holdout не трогаем до конца.

### 1. Все поля схемы для LLM обязательны

- **Что сломалось.** «аренда 3-комнатной в Алматы» (d03) терял город в 2 прогонах из 3.
- **Почему.** Не ошибка разбора: ключа `city` не было уже в сыром JSON модели
  (`{"deal_type":"rent","rooms":[3],"features":[],...}`). Поля с default не входят в
  `required` схемы, и structured outputs разрешают модели их пропускать — она
  пропускала поля непредсказуемо (`districts` то был, то нет), в том числе нужные.
- **Что сделали.** В `build_parser_schema` все поля без default: модель обязана
  явно решить по каждому полю, «нет фильтра» пишет как `null` / `[]` / `""`.
  `SearchFilters` для кода не изменился. Правка общая — для всех полей, не для d03.
- **Результат.** d03: 1/3 → 3/3. Разброс между повторами 3% → 0%. Задержка та же.

### 2. Правило о правдоподобной цене

- **Что сломалось.** «трёхкомнатная в Алматы за 3 миллиона тенге» (d20) — 0/3: модель
  без вопросов ставила `price_max_kzt=3000000`, и поиск честно вернул бы пусто.
- **Почему.** Промпт требовал уточнения только для запросов «не про недвижимость,
  невыполним или слишком размыт» — неправдоподобную цену модель невыполнимой не считала.
- **Что сделали.** Общее правило в `parse_query.md`: цена на порядок ниже или выше
  рыночной для такой квартиры и типа сделки (опечатка, перепутаны тысячи и миллионы) →
  `needs_clarification` с вопросом про цену, цену не заполнять. Порогов в промпте нет,
  чтобы не подгонять под d20.
- **Результат.** d20: 0/3 → 3/3, dev 95% → 100% ± 0%. Ложных уточнений нет: все 9 dev-кейсов
  с нормальной ценой проходят 3/3.
- **Оговорка.** 100% на dev — потолок для набора, который писался вместе с промптом.
  Обобщение покажет holdout.

### Итог шага 2: holdout

Финальный промпт (`parse_query.md` после правки 2) один раз прогнан на holdout — 10 кейсов,
написанных отдельно от промпта и не виденных при его правке.

| Набор | Полностью верных ×3 | p50 / p95 | Отчёт |
| --- | --- | --- | --- |
| dev (20) | 100% ± 0% | 2,0 / 3,0 с | `evals/results/20261103T124759Z_parse_dev_x3.json` |
| holdout (10) | 97% ± 6% (90–100%) | 2,6 / 3,5 с | `evals/results/20261103T125516Z_parse_holdout_x3.json` |

Цель шага (не меньше 90% полностью верных) выполнена на обоих наборах.

- **Единственный сбой — h09** (теги `edge`, `currency`), 2/3: в одном прогоне модель вместо
  уточнения пересчитала цену в тенге сама (`price_max_kzt=50000000`). Правило о
  неправдоподобной цене не покрывает цену в другой валюте.
- **Не исправляли.** Правка под holdout сделала бы его ещё одним dev. Если чинить: общее
  правило «цены только в тенге; другая валюта → уточнение», сначала новый dev-кейс с валютой,
  затем свежий holdout для проверки.

## Поиск

### Данные для разметки: подложенные объекты

- **Проблема.** На 1000 синтетических объектах у 5 из 25 размечаемых кейсов под
  `expected_filters` не было ни одного объекта (d10, d12, d14, h04, h05), у d13 — два.
  Для пустого эталона Recall@10 не определён.
- **Что сделали.** `scripts/seed_listings.py` для кейсов, где под фильтры меньше 3 объектов,
  подкладывает 4 подходящих объекта и 4 обманки (`source_id` с префиксом `seed-`, роли — в
  `data/seed_manifest.jsonl`). Поля задаёт скрипт и проверяет, что подходящие проходят все
  фильтры, а каждая обманка нарушает ровно один. LLM пишет только текст и получает поля и
  пересказ смысла (`intent`), но не текст запроса; описания с 3+ словами запроса подряд
  отбрасываются локальной проверкой. При разметке `source_id` скрыт, подложенные объекты
  подходящими автоматически не считаются.
- **Обманки двух видов.** «Фильтры без смысла» попадают в пул и в выдачу и проверяют
  ранжирование. «Смысл без фильтра» под жёсткими SQL-фильтрами в пул и выдачу не попадают:
  они нужны для ослабления фильтров (п. 6) и сквозного прогона через парсер, где фильтр может
  быть распознан неверно.
- **Результат для dev.** Под фильтры подходит: d10 0 → 4, d12 0 → 4, d13 2 → 6, d14 0 → 4.
  У четырёх dev-кейсов `intent` пустой (`semantic: empty`), поэтому их обманки — только с
  нарушенным фильтром. Holdout: h04 0 → 6 (4 подходящих + 2 обманки «фильтры без смысла»), h05 0 → 4
  (`intent` для них писал автор holdout).
- **Повторный запуск не трогает готовое.** Первая версия скрипта при каждом запуске заново
  генерировала все цели; так dev-тексты были перегенерированы до коммита (поля те же —
  генератор детерминирован по id кейса, тексты новые). Теперь уже подложенные кейсы
  пропускаются, заново — только по `--regen <id>`.

### Эталон для кейсов без смысловых требований — автоматически

- **Что сломалось.** При ручной разметке d02 и d03 под фильтры подходило 64 и 60 объектов, а
  в пуле кандидатов — 30. Эталон получался неполным, Recall — заниженным.
- **Что сделали.** Для `semantic: empty` эталон = все объекты, проходящие `expected_filters`,
  считается скриптом (`"relevance": "auto"`). Вручную размечаются только `semantic: required`
  (7 кейсов). Ручная разметка d01–d04 заменена автоматической; она целиком входила в неё
  (d02: 30 → 64, d03: 30 → 60, d01 и d04 без изменений).
- **Следствие.** На эталонных фильтрах у `auto`-кейсов Recall@10 близок к 100% по построению.
  Ранжирование меряют 7 `manual`-кейсов; `auto`-кейсы информативны в сквозном прогоне через
  парсер. В отчёте поиска — отдельная разбивка.

### Смысловые кейсы размечены LLM и проверены вручную

- **Что сломалось.** Ручная разметка 7 смысловых кейсов (`semantic: required`) вышла неполной
  (размечен один кейс из семи) и непоследовательной: в d15 «рядом горы» без вида было отмечено
  подходящим, а пять кандидатов с видом на горы и тишиной в описании — нет. Векторный поиск
  получал на d15 Recall 0%, хотя его топ-5 подходил по правилам.
- **Что сделали.** `scripts/llm_label.py review`: LLM (`models.labeler`, Opus) решает
  «подходит / нет» по тому же пулу из 30 кандидатов и по тем же правилам — раздел правил берётся
  из `docs/labeling.md`, — с одной строкой причины. Решения идут в `evals/llm_labels_review.md`,
  человек их проверяет и правит; `apply` переносит их в `cases.jsonl` с
  `"relevance": "llm_reviewed"`. Ручная разметка d15 заменена. Holdout-запросы и решения по
  ним в консоль не выводятся: их проверяет только автор holdout.
- **Почему так.** LLM применяет правило одинаково ко всем кандидатам, причина в каждой строке
  делает решения проверяемыми, а финальное слово остаётся за человеком.
- **Результат.** 7 кейсов перенесены с `"relevance": "llm_reviewed"` после проверки. Dev:
  d15 — 12 подходящих из 30 (было 6 вручную), d17 — 2, d16 — 0: ни у одного кандидата описание не
  подтверждает одновременно «светлая» и «рядом с парком» (по строгому правилу «сомневаешься —
  не подходит»), кейс уходит в «без подходящих» и в среднее не входит. Holdout размечен и проверен, цифры по нему здесь не приводятся.
- **Ограничение.** В группе «ранжирование решает» на dev остаются d15 и d17 — мало для выводов
  о ранжировании; вывод по ней делаем вместе с holdout.

### Замер: только векторы (dev, эталонные фильтры)

Поиск на `expected_filters` кейса (без парсера), эмбеддинг запроса `voyage-3.5` (1024),
сортировка по косинусному расстоянию внутри жёстких SQL-фильтров. Recall@10 = попаданий /
min(|подходящих|, 10), MRR — по топ-10. Отчёт: `evals/results/20261104T054701Z_search_vector_dev.json`.

| Группа | Кейсов | Recall@10 | MRR |
| --- | --- | --- | --- |
| Ранжирование решает (смысл + кандидатов > 10) | 2 | 45% | 0,56 |
| Остальные (эталон = все объекты под фильтрами) | 14 | 100% | 1,00 |
| Все | 16 | 93% | 0,94 |

SQL p50 1 мс, p95 5 мс (без эмбеддинга запроса). d16 без подходящих — не в среднем.

- **d15** «тихая квартира с видом на горы»: первое место подходит (RR 1,0), но в топ-10 из 12
  подходящих только 4 (места 1, 3, 4, 5), остальные — 14–40. «Вид на горы» векторы ловят,
  второе требование («тихо») ранжируют слабо.
- **d17** «аренда рядом со школой, чтобы окна во двор»: первый подходящий — на 8-м месте. Места
  1–7 — объявления со словами «школа» и «двор» («двор тихий», «школа во дворе»), но без «окон во
  двор»: эмбеддинг всего запроса тянет общую тему, конкретная формулировка теряется. Это то, что
  должен добавить полнотекстовый поиск в гибриде.
- **Вывод.** «Остальные» = 100% по построению (см. «Эталон для кейсов без смысловых требований»).
  Вся разница между методами будет видна на группе «ранжирование решает», а на dev в ней два
  кейса — сравнение с гибридом читаем как направление, не как точную цифру.

### Дооценка разметки и замер: векторы vs гибрид (dev v2, эталонные фильтры)

**Дооценка.** Первый прогон обоих методов дал 10 неразмеченных объектов в топ-10 гибрида
(d22 — 2, d28 — 2, d29 — 3, d30 — 3; у векторов — 0). `llm_label.py extend` разметил только их,
проверено без правок (`evals/llm_labels_extend_1.md`), `apply --merge` добавил к прежней разметке:
d22 12 → 13 подходящих, d29 13 → 16, d28 и d30 без новых. Повторный прогон — неразмеченных в
топ-10 нет ни у одного метода. Цифры ниже — оба метода в одном прогоне, на одной разметке и одних
эмбеддингах запросов. Отчёт: `evals/results/20261104T061403Z_search_vector+hybrid_dev.json`.

**Гибрид:** внутри жёстких SQL-фильтров топ-50 векторов и топ-50 полнотекстового поиска
(`ts_rank_cd`, запрос по OR), слияние RRF с k = 60. Полнотекстовый — по OR, а не по AND из
дизайна: на целом запросе AND почти не находит совпадений, и гибрид выродился бы в векторы.

| Метод | Ранжирование решает (12): Recall@10 | MRR | Остальные (14): Recall@10 | SQL p50 / p95 |
| --- | --- | --- | --- | --- |
| Только векторы | 47% | 0,70 | 100% | 1 / 3 мс |
| Гибрид (векторы + полнотекстовый, RRF) | **62%** | **0,79** | 100% | 1 / 3 мс |

По кейсам группы «ранжирование решает» (d16 — без подходящих, не в среднем):

| Кейс | Запрос | Векторы R@10 / RR | Гибрид R@10 / RR |
| --- | --- | --- | --- |
| d15 | тихая квартира с видом на горы в Алматы | 40% / 1,00 | 70% / 1,00 |
| d17 | квартира в аренду рядом со школой, чтобы окна во двор, Алматы | 50% / 0,12 | 50% / 0,20 |
| d21 | квартира в Астане с видом на город | 50% / 1,00 | 80% / 1,00 |
| d22 | снять жильё в Алматы недалеко от парка | 10% / 0,33 | 50% / 1,00 |
| d23 | аренда в Астане, кухня большая, люблю готовить | 30% / 0,33 | 50% / 1,00 |
| d24 | ищу квартиру в кирпичном доме в Алматы, бюджет до 40 млн | 22% / 1,00 | 22% / 1,00 |
| d25 | Астана, чтобы остановка была рядом, езжу на автобусе | 70% / 1,00 | 90% / 1,00 |
| d26 | квартира в Алматы с панорамными окнами | 80% / 1,00 | 100% / 1,00 |
| d27 | сниму двушку в Алматы, важны спокойные соседи | 12% / 0,12 | 75% / 0,50 |
| d28 | квартира в Астане, чтобы в доме была охрана или консьерж | 75% / 1,00 | 25% / 0,50 |
| d29 | Алматы, хочу зелёный двор с деревьями | 20% / 0,50 | 60% / 0,33 |
| d30 | аренда в Алматы, у меня кот, нужно чтобы пускали с животными | 100% / 1,00 | 67% / 1,00 |

- **Где гибрид выиграл** (8 кейсов из 12): конкретное слово-признак в запросе, которое
  эмбеддинг всего запроса размывает — «соседи» (d27 12% → 75%), «парк» (d22 10% → 50%),
  «двор… деревья» (d29 20% → 60%), «кухня» (d23 30% → 50%), «вид на город» (d21 50% → 80%).
- **Где проиграл:**
  - **d28** «охрана или консьерж» 75% → 25%. Запрос по OR включает общие слова
    (`'квартир' | 'астан' | 'дом' | …`), которые есть почти в каждом `search_text`; `ts_rank_cd`
    не учитывает редкость слова (нет IDF), и наверх выходят длинные тексты с общими словами.
    Это разрыв между `ts_rank_cd` и BM25, о котором предупреждает дизайн.
  - **d30** «пускали с животными» 100% → 67%: в топ попало «Сдаём семье, без животных» —
    полнотекстовый поиск не понимает отрицание.
- **Без изменений:** d24 «кирпичный дом» 22% у обоих, d17 «окна во двор» 50% у обоих.
- **Вывод.** Гибрид лучше в среднем (+15 п. п. Recall@10, +0,09 MRR) при той же задержке, но
  проигрывает там, где общие слова запроса забивают полнотекстовый ранг. Кандидаты на следующий
  шаг: полнотекстовый поиск только по смысловой части запроса (`semantic_query` от парсера — в
  сквозном прогоне она уже без города и «квартиры») или отсев частых слов / настоящий BM25.
  Решение — после сквозного прогона через парсер. 12 кейсов — мало; holdout не гоняли.

### Ослабление фильтров (п. 6)

- **Поведение.** `search()` в `app/search/hybrid.py`: только если строгие фильтры дали **0**,
  по очереди и накопительно снимаются мягкие фильтры `features` → `conditions` → `districts`,
  остановка на первом непустом шаге; шаг, где фильтр не задан, пропускается. Жёсткие (город,
  сделка, комнаты, цена, площадь) не ослабляются никогда — иначе честный ноль. Возвращается и
  список снятых фильтров: ответ (шаг 4) обязан сказать, что ослаблено. Порог «меньше K» не берём:
  узкий, но честный запрос размывался бы объектами, не проходящими фильтр.
- **Проверка — набор `relax`** (`split: relax`, 6 кейсов), строгие фильтры в данных дают 0.
  Основные — реалистичные сочетания «район + состояние + признак», которые парсер пропустит
  (r01–r05, в том числе r05 со снятием до района); r06 «однушка у метро в Астане» — с пометкой:
  в сквозном потоке его остановит парсер. Итог для векторов и гибрида: снято ровно ожидаемое —
  6/6, весь топ-10 проходит оставшиеся фильтры — 6/6
  (`evals/results/20261104T062200Z_relax_vector+hybrid.json`).
- **Регрессия на dev.** Ослабление на dev не сработало ни разу (у всех кейсов строгие фильтры
  что-то находят). Метрики: векторы 47% / 0,70, гибрид 61% / 0,79 против 62% / 0,79 в прошлом
  прогоне — см. следующий пункт.
- **d16** (0 подходящих при 45 объектах под фильтрами) к ослаблению не относится: фильтры
  находят объекты, не подходит смысл. Его честный ноль — задача ответа (шаг 4).

### Шум эмбеддингов запросов между прогонами

Voyage возвращает для одного и того же текста идентичный вектор внутри одного запроса, но слегка
разный в разных запросах (L2 ≈ 0,01, макс. разница координаты ≈ 0,001). Почти равные по
близости объекты меняют места: между прогонами dev d03 и d29 переставились соседние позиции,
гибрид — 62% ↔ 61%. Внутри одного прогона все методы считаются на одних векторах, сравнение
корректно; между прогонами разница в 1 п. п. — шум, а не эффект.

### HNSW на текущем объёме не используется

На 1048 объектах планировщик выбирает btree-индекс `(city, deal_type, rooms, price_kzt)` и
сортировку по расстоянию — это точный перебор, HNSW-индекс не участвует, потерь полноты от него
нет. Сравнение HNSW + `iterative_scan` с точным перебором отложено до объёма прода.

### Кэш эмбеддингов запросов; итог шага 3

- **Кэш.** `evals/query_embeddings.jsonl`: ключ — модель + тип ввода + размерность + текст;
  новые тексты считаются одним батчем и дописываются. Повторный прогон берёт векторы из кэша —
  два подряд прогона dev дали одинаковый топ-10 во всех кейсах.
- **Зафиксированные цифры dev v2 (с кэшем,
  `evals/results/20261104T062816Z_search_vector+hybrid_dev.json`):**

| Метод | Ранжирование решает (12): Recall@10 | MRR | Остальные (14): Recall@10 |
| --- | --- | --- | --- |
| Только векторы | 47% | 0,70 | 100% |
| Гибрид (RRF) | 62% | 0,79 | 100% |

- **Holdout — один прогон** (`evals/results/20261104T062632Z_search_vector+hybrid_holdout.json`,

  под фильтры 6 объектов. Остальные 5 кейсов — 100% у обоих методов. О ранжировании holdout
  ничего не говорит: вывод «гибрид лучше» опирается только на dev (12 кейсов).

### Находка: искать нужно по смысловой части запроса, а не по всему тексту

- **Наблюдение.** В сквозном прогоне (фильтры от парсера) поиск оказался лучше, чем на эталонных
  фильтрах, хотя фильтры те же: парсер разобрал все 27 кейсов dev полностью верно.
- **Проверка.** Фильтры от парсера совпадают с эталонными в 27 из 27 кейсов (единственное
  расхождение — порядок в списке `conditions` у d11, на SQL не влияет). Поиск на **эталонных**
  фильтрах, но по тексту `semantic_query` от парсера, дал топ-10, совпадающий с вариантом «от
  парсера», в 27 из 27 кейсов и у векторов, и у гибрида. Значит, вся разница — в тексте поиска.
- **Почему.** На эталонных фильтрах `semantic_query` нет, и эмбеддинг и полнотекстовый поиск
  строятся по всему запросу: «снять жильё в Алматы недалеко от парка». Парсер оставляет только
  смысл: «недалеко от парка», «спокойные соседи», «окна во двор». Город, сделка и «квартира» уже
  проверены SQL-фильтрами; в тексте поиска они только размывают эмбеддинг и забивают
  полнотекстовый ранг общими словами (тот же механизм, что у провала гибрида на d28).
- **Следствия.**
  - Поиск в продукте берёт `query_text(filters)` = `semantic_query` — так уже сделано в коде.
  - Отложенное «FTS только по смысловой части» фактически получено бесплатно через парсер.
    Отдельно остаётся проверить отсев частых слов / BM25 — уже на `semantic_query`.
  - Сравнения поиска дальше ведём на сквозном варианте («от парсера»): он ближе к продукту.
    Вариант на эталонных фильтрах оставляем как контроль, что ошибки разбора не прячут проблемы.
  - Парсер недетерминирован: формулировка `semantic_query` плавает от прогона к прогону, топ-10
    меняется, всплывают новые неразмеченные. Поэтому сравнения и дооценка идут на фильтрах одного
    прогона: `--parsed-from <отчёт>`.

### Реранкер: Voyage rerank-3 vs rerank-2.5 (dev v2, фильтры от парсера)

**Что.** `app/search/rerank.py`: топ-50 гибрида переранжируется Voyage `/v1/rerank` по
`search_text`; запрос — `semantic_query` (или весь запрос, если смысловой части нет). Модель и
число кандидатов — `rerank` в конфиге. В evals порядок от реранкера кэшируется
(`evals/rerank_cache.jsonl`: модель + запрос + кандидаты) — повторные прогоны бесплатны и
одинаковы. Формат запроса и модели сверены с документацией Voyage: актуальная — `rerank-3`,
явно многоязычной документация называет `rerank-2.5`.

**Дооценка.** После реранка в топ-10 — 21 неразмеченный объект (11 у `rerank-3`, 10 у
`rerank-2.5`); 14 уникальных размечены LLM, проверены без правок (`evals/llm_labels_extend_4.md`),
10 подходят. Повторный прогон — неразмеченных нет ни в одном варианте. Фильтры от парсера —
из `20261105T052638Z`. Отчёт:
`evals/results/20261105T061507Z_search_hybrid+rerank:rerank-3+rerank:rerank-2.5_parsed_dev.json`.

| Вариант | Ранжирование решает (12): Recall@10 | MRR | Остальные (14) |
| --- | --- | --- | --- |
| гибрид | 72% | 0,90 | 100% |
| гибрид + `rerank-3` | 98% | 1,00 | 100% |
| гибрид + `rerank-2.5` | 98% | 1,00 | 100% |

(Гибрид 74% → 72% против прошлой таблицы — дооценка нашла больше подходящих, знаменатель вырос.)

**Оговорки.**
- **Потолок.** 98% / 1,00 на 12 кейсах — dev для реранкера стал лёгким; модели на нём
  неразличимы.
- **Общая предвзятость.** Эталон смысловых кейсов размечает LLM, реранкер — тоже смысловая
  модель; они могут сходиться на одних признаках и завышать цифру. Ограничивает это только
  ручная проверка каждой дооценки.
- **Holdout** реранкер пока не проверяет: из четырёх смысловых кейсов h04 и h08 — объектов под
  фильтрами меньше 10 (порядок не решает), у h06 и h07 (39 и 125 объектов) среди 30 оценённых
  подходящих нет. Реранкер может поднять подходящие из неоценённых — нужен прогон на holdout с
  дооценкой.

**Вывод.** Реранкер явно помогает: +26 п. п. Recall@10, MRR до 1,00. Выбор модели — по задержке и
цене (ниже); при похожих значениях — `rerank-2.5` как явно многоязычная.

**Задержка и цена без кэша** (`evals/results/rerank_latency_dev.json`): по 8 запросов на модель,
полный набор из 50 кандидатов (как в продукте), время только успешного HTTP-запроса — ожидание
после 429 не считается; токены — из `usage` ответа, цена — $0,05 за 1 млн токенов (200 млн
бесплатно) по прайсу Voyage.

| Модель | p50 | p95 (= макс. из 8) | Токенов на запрос | $ на запрос |
| --- | --- | --- | --- | --- |
| `rerank-3` | 628 мс | 950 мс | ~6 300 | $0,00032 |
| `rerank-2.5` | 562 мс | 708 мс | ~6 300 | $0,00032 |

Первый замер (по первым 8 записям кэша) вышел смещённым: там были простые кейсы с 14–50
кандидатами, ~2 700 токенов и заниженные задержка и цена — перемерено на полных наборах.

**Решение:** `rerank-2.5` — качество на dev то же, задержка не хуже, явно многоязычная по
документации. Цена реранка ≈ $0,0003 за поиск, первые ~30 тыс. поисков — бесплатно.
Реранк добавляет к поиску ~0,6 с — заметно на фоне SQL (1–5 мс), учитываем в бюджете ответа.
