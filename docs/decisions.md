# Решения по качеству

Что сломалось, почему, что исправили и цифры до/после. Метрика разбора — доля
полностью верных `SearchFilters` на dev (20 кейсов), каждая конфигурация гоняется
×3; указаны среднее ± стандартное отклонение по повторам. Holdout не трогаем до конца.

### 1. Все поля схемы для LLM обязательны

- **Что сломалось.** «аренда 3-комнатной в Алматы» (d03) терял город в 2 прогонах из 3.
- **Почему.** Не ошибка разбора: ключа `city` не было уже в сыром JSON модели
  (`{"deal_type":"rent","rooms":[3],"features":[],...}`). Поля с default не входят в
  `required` схемы, и structured outputs разрешают модели их пропускать — она
  пропускала поля непредсказуемо (`districts` то был, то нет), в том числе нужные.
- **Что сделали.** В `build_parser_schema` все поля без default: модель обязана
  явно решить по каждому полю, «нет фильтра» пишет как `null` / `[]` / `""`.
  `SearchFilters` для кода не изменился. Правка общая — для всех полей, не для d03.
- **Результат.** d03: 1/3 → 3/3. Разброс между повторами 3% → 0%. Задержка та же.

### 2. Правило о правдоподобной цене

- **Что сломалось.** «трёхкомнатная в Алматы за 3 миллиона тенге» (d20) — 0/3: модель
  без вопросов ставила `price_max_kzt=3000000`, и поиск честно вернул бы пусто.
- **Почему.** Промпт требовал уточнения только для запросов «не про недвижимость,
  невыполним или слишком размыт» — неправдоподобную цену модель невыполнимой не считала.
- **Что сделали.** Общее правило в `parse_query.md`: цена на порядок ниже или выше
  рыночной для такой квартиры и типа сделки (опечатка, перепутаны тысячи и миллионы) →
  `needs_clarification` с вопросом про цену, цену не заполнять. Порогов в промпте нет,
  чтобы не подгонять под d20.
- **Результат.** d20: 0/3 → 3/3, dev 95% → 100% ± 0%. Ложных уточнений нет: все 9 dev-кейсов
  с нормальной ценой проходят 3/3.
- **Оговорка.** 100% на dev — потолок для набора, который писался вместе с промптом.
  Обобщение покажет holdout.

### Итог шага 2: holdout

Финальный промпт (`parse_query.md` после правки 2) один раз прогнан на holdout — 10 кейсов,
написанных отдельно от промпта и не виденных при его правке.

| Набор | Полностью верных ×3 | p50 / p95 | Отчёт |
| --- | --- | --- | --- |
| dev (20) | 100% ± 0% | 2,0 / 3,0 с | `evals/results/20261103T124759Z_parse_dev_x3.json` |
| holdout (10) | 97% ± 6% (90–100%) | 2,6 / 3,5 с | `evals/results/20261103T125516Z_parse_holdout_x3.json` |

Цель шага (не меньше 90% полностью верных) выполнена на обоих наборах.

- **Единственный сбой — h09** (теги `edge`, `currency`), 2/3: в одном прогоне модель вместо
  уточнения пересчитала цену в тенге сама (`price_max_kzt=50000000`). Правило о
  неправдоподобной цене не покрывает цену в другой валюте.
- **Не исправляли.** Правка под holdout сделала бы его ещё одним dev. Если чинить: общее
  правило «цены только в тенге; другая валюта → уточнение», сначала новый dev-кейс с валютой,
  затем свежий holdout для проверки.

## Поиск

### Данные для разметки: подложенные объекты

- **Проблема.** На 1000 синтетических объектах у 5 из 25 размечаемых кейсов под
  `expected_filters` не было ни одного объекта (d10, d12, d14, h04, h05), у d13 — два.
  Для пустого эталона Recall@10 не определён.
- **Что сделали.** `scripts/seed_listings.py` для кейсов, где под фильтры меньше 3 объектов,
  подкладывает 4 подходящих объекта и 4 обманки (`source_id` с префиксом `seed-`, роли — в
  `data/seed_manifest.jsonl`). Поля задаёт скрипт и проверяет, что подходящие проходят все
  фильтры, а каждая обманка нарушает ровно один. LLM пишет только текст и получает поля и
  пересказ смысла (`intent`), но не текст запроса; описания с 3+ словами запроса подряд
  отбрасываются локальной проверкой. При разметке `source_id` скрыт, подложенные объекты
  подходящими автоматически не считаются.
- **Обманки двух видов.** «Фильтры без смысла» попадают в пул и в выдачу и проверяют
  ранжирование. «Смысл без фильтра» под жёсткими SQL-фильтрами в пул и выдачу не попадают:
  они нужны для ослабления фильтров (п. 6) и сквозного прогона через парсер, где фильтр может
  быть распознан неверно.
- **Результат для dev.** Под фильтры подходит: d10 0 → 4, d12 0 → 4, d13 2 → 6, d14 0 → 4.
  У четырёх dev-кейсов `intent` пустой (`semantic: empty`), поэтому их обманки — только с
  нарушенным фильтром. Holdout: h04 0 → 6 (4 подходящих + 2 обманки «фильтры без смысла»), h05 0 → 4
  (`intent` для них писал автор holdout).
- **Повторный запуск не трогает готовое.** Первая версия скрипта при каждом запуске заново
  генерировала все цели; так dev-тексты были перегенерированы до коммита (поля те же —
  генератор детерминирован по id кейса, тексты новые). Теперь уже подложенные кейсы
  пропускаются, заново — только по `--regen <id>`.

### Эталон для кейсов без смысловых требований — автоматически

- **Что сломалось.** При ручной разметке d02 и d03 под фильтры подходило 64 и 60 объектов, а
  в пуле кандидатов — 30. Эталон получался неполным, Recall — заниженным.
- **Что сделали.** Для `semantic: empty` эталон = все объекты, проходящие `expected_filters`,
  считается скриптом (`"relevance": "auto"`). Вручную размечаются только `semantic: required`
  (7 кейсов). Ручная разметка d01–d04 заменена автоматической; она целиком входила в неё
  (d02: 30 → 64, d03: 30 → 60, d01 и d04 без изменений).
- **Следствие.** На эталонных фильтрах у `auto`-кейсов Recall@10 близок к 100% по построению.
  Ранжирование меряют 7 `manual`-кейсов; `auto`-кейсы информативны в сквозном прогоне через
  парсер. В отчёте поиска — отдельная разбивка.

### Смысловые кейсы размечены LLM и проверены вручную

- **Что сломалось.** Ручная разметка 7 смысловых кейсов (`semantic: required`) вышла неполной
  (размечен один кейс из семи) и непоследовательной: в d15 «рядом горы» без вида было отмечено
  подходящим, а пять кандидатов с видом на горы и тишиной в описании — нет. Векторный поиск
  получал на d15 Recall 0%, хотя его топ-5 подходил по правилам.
- **Что сделали.** `scripts/llm_label.py review`: LLM (`models.labeler`, Opus) решает
  «подходит / нет» по тому же пулу из 30 кандидатов и по тем же правилам — раздел правил берётся
  из `docs/labeling.md`, — с одной строкой причины. Решения идут в `evals/llm_labels_review.md`,
  человек их проверяет и правит; `apply` переносит их в `cases.jsonl` с
  `"relevance": "llm_reviewed"`. Ручная разметка d15 заменена. Holdout-запросы и решения по
  ним в консоль не выводятся: их проверяет только автор holdout.
- **Почему так.** LLM применяет правило одинаково ко всем кандидатам, причина в каждой строке
  делает решения проверяемыми, а финальное слово остаётся за человеком.
- **Результат.** 7 кейсов перенесены с `"relevance": "llm_reviewed"` после проверки. Dev:
  d15 — 12 подходящих из 30 (было 6 вручную), d17 — 2, d16 — 0: ни у одного кандидата описание не
  подтверждает одновременно «светлая» и «рядом с парком» (по строгому правилу «сомневаешься —
  не подходит»), кейс уходит в «без подходящих» и в среднее не входит. Holdout размечен и проверен, цифры по нему здесь не приводятся.
- **Ограничение.** В группе «ранжирование решает» на dev остаются d15 и d17 — мало для выводов
  о ранжировании; вывод по ней делаем вместе с holdout.

### Замер: только векторы (dev, эталонные фильтры)

Поиск на `expected_filters` кейса (без парсера), эмбеддинг запроса `voyage-3.5` (1024),
сортировка по косинусному расстоянию внутри жёстких SQL-фильтров. Recall@10 = попаданий /
min(|подходящих|, 10), MRR — по топ-10. Отчёт: `evals/results/20261104T054701Z_search_vector_dev.json`.

| Группа | Кейсов | Recall@10 | MRR |
| --- | --- | --- | --- |
| Ранжирование решает (смысл + кандидатов > 10) | 2 | 45% | 0,56 |
| Остальные (эталон = все объекты под фильтрами) | 14 | 100% | 1,00 |
| Все | 16 | 93% | 0,94 |

SQL p50 1 мс, p95 5 мс (без эмбеддинга запроса). d16 без подходящих — не в среднем.

- **d15** «тихая квартира с видом на горы»: первое место подходит (RR 1,0), но в топ-10 из 12
  подходящих только 4 (места 1, 3, 4, 5), остальные — 14–40. «Вид на горы» векторы ловят,
  второе требование («тихо») ранжируют слабо.
- **d17** «аренда рядом со школой, чтобы окна во двор»: первый подходящий — на 8-м месте. Места
  1–7 — объявления со словами «школа» и «двор» («двор тихий», «школа во дворе»), но без «окон во
  двор»: эмбеддинг всего запроса тянет общую тему, конкретная формулировка теряется. Это то, что
  должен добавить полнотекстовый поиск в гибриде.
- **Вывод.** «Остальные» = 100% по построению (см. «Эталон для кейсов без смысловых требований»).
  Вся разница между методами будет видна на группе «ранжирование решает», а на dev в ней два
  кейса — сравнение с гибридом читаем как направление, не как точную цифру.
