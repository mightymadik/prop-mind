# prop-mind: AI-поиск недвижимости — дизайн

Nov 3, 2026 · @Madiyar Bizhanov

## Цель и критерии готовности

Сервис, где пользователь пишет запрос обычным языком («2-комнатная у метро до 40 млн с ремонтом»), а система находит подходящие объекты и объясняет, почему выбрала именно их. Проект показывает работодателю то, что просят в вакансиях: structured outputs, tool use, гибридный поиск, реранкинг и, главное, качество, измеренное в цифрах.

Проект готов (неделя 4), когда:

- разбор запроса в фильтры правильный не меньше чем в 90% тестовых случаев;
- Recall@10 замерен на 30 запросах и записан в README, со сравнением «только векторы» против «гибрид + реранкинг»;
- для каждого запроса логируются задержка и стоимость;
- есть демо: простая веб-страница или Swagger и видео на 2–3 минуты;
- всё запускается одной командой `docker compose up`.

Главный принцип: LLM не «ищет» сама и не выдумывает объекты. Она переводит запрос в фильтры и в конце объясняет результат, а находит объекты база. Так ответы проверяемы, а галлюцинаций про несуществующие квартиры нет.

**Две версии, и это ваша история для интервью:**

- **v1, фиксированный workflow (недели 1–3).** Шаги всегда идут в одном порядке, как на схеме. Это дёшево, предсказуемо и легко измеряется evals. Статья Anthropic «Building effective agents» прямо советует начинать с такого простого варианта.
- **v2, tool use (неделя 4 или позже).** Модель сама вызывает инструмент `search_listings`, может уточнить запрос («какой район?») или повторить поиск с ослабленными фильтрами, если ничего не нашлось. Сравните v1 и v2 на одних и тех же evals по точности, задержке и цене: такое сравнение отлично смотрится в README и на собеседовании.

## Данные и схема БД

**Откуда взять 2–3 тыс. объектов.** Лучший вариант — данные с работы, если разрешат: обезличенные, без телефонов и имён. Запасной — синтетика: генерируете объявления через Claude пачками по 50, задав распределение по городам, районам, ЖК, цене и состоянию. Просите разнообразие живого языка: «евродвушка», «в шаговой доступности от метро», «под ипотеку», опечатки. Учтите реальность: метро есть только в Алматы, поэтому запрос «у метро в Астане» должен честно возвращать пустой результат или уточнение.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE listings (
  id            BIGSERIAL PRIMARY KEY,
  city          TEXT NOT NULL,              -- 'Алматы', 'Астана'
  district      TEXT,
  complex_name  TEXT,                       -- ЖК
  deal_type     TEXT NOT NULL CHECK (deal_type IN ('sale', 'rent')),
  rooms         SMALLINT,
  area_m2       NUMERIC(6,1),
  floor         SMALLINT,
  floors_total  SMALLINT,
  year_built    SMALLINT,
  condition     TEXT CHECK (condition IN ('rough', 'pre_finish', 'renovated', 'designer')),
  price_kzt     BIGINT NOT NULL,
  features      TEXT[] NOT NULL DEFAULT '{}', -- 'near_metro', 'parking', 'mortgage', ...
  description   TEXT NOT NULL,
  search_text   TEXT NOT NULL,              -- поля + описание, см. ниже
  tsv           tsvector GENERATED ALWAYS AS (to_tsvector('russian', search_text)) STORED,
  embedding     vector(1024),               -- размерность = размерность вашей модели
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX ON listings USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON listings USING gin (tsv);
CREATE INDEX ON listings USING gin (features);
CREATE INDEX ON listings (city, deal_type, rooms, price_kzt);

-- журнал запросов: основа для отладки, стоимости и будущих evals
CREATE TABLE query_log (
  id          BIGSERIAL PRIMARY KEY,
  query       TEXT NOT NULL,
  filters     JSONB,
  result_ids  BIGINT[],
  latency_ms  INT,
  cost_usd    NUMERIC(10,6),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**`search_text` — это ваш contextual retrieval.** Перед описанием приклейте структурированный контекст: «2-комнатная квартира, 64 м², ЖК Хан Тенгри, Бостандыкский район, Алматы, с ремонтом, рядом метро. {описание}». Тогда и эмбеддинг, и полнотекстовый поиск видят характеристики, которых продавец мог не написать в тексте. Это та же идея, что в статье Anthropic про Contextual Retrieval, только контекст собирается из полей, а не генерируется LLM.

**Эмбеддинги.** У Anthropic нет своей модели эмбеддингов, поэтому возьмите модель с хорошим русским: Voyage (её рекомендует документация Claude), OpenAI text-embedding-3 или открытую multilingual-e5-large. Размерность колонки `vector(…)` поставьте под выбранную модель. Хорошее упражнение для README — сравнить две модели на ваших evals.

## Разбор запроса

Задача шага: превратить свободный текст в строгую структуру, которую проверяет Pydantic. Используйте `Literal` вместо `Enum`: JSON-схема получается плоской, без `$defs`, и модель её надёжнее заполняет.

```python
from typing import Literal
from pydantic import BaseModel, Field

Feature = Literal["near_metro", "parking", "mortgage", "new_building", "near_school", "furnished"]

class SearchFilters(BaseModel):
    city: Literal["Алматы", "Астана"] | None = None
    deal_type: Literal["sale", "rent"] = "sale"
    rooms: list[int] | None = Field(None, description="Допустимое число комнат. 'Евродвушка' = [2]")
    price_min_kzt: int | None = None
    price_max_kzt: int | None = None
    area_min_m2: float | None = None
    districts: list[str] | None = None
    conditions: list[Literal["rough", "pre_finish", "renovated", "designer"]] | None = None
    features: list[Feature] = []
    semantic_query: str = Field("", description="То, что не выражается полями: 'тихий двор', 'вид на горы'")
    needs_clarification: str | None = Field(None, description="Вопрос пользователю, если запрос невыполним или слишком размыт")
```

JSON получаем через structured outputs: схема ответа задаётся в запросе, и модель обязана ей следовать. Раньше здесь был принудительный вызов инструмента (`tool_choice`), но на актуальных моделях он отклоняется API, а SDK 2.x не принимает `temperature`. Стабильность разбора держится на схеме, валидации Pydantic и evals. Tool use остаётся для v2, где модель сама решает, звать ли поиск.

Вызов идёт через обёртку `call_structured` из `app/llm/client.py`. Внутри — `client.messages.stream(..., output_format=SearchFilters)`: SDK сам приводит схему Pydantic к требованиям API (`additionalProperties: false` у каждого объекта, `required`) и валидирует ответ. Сырой `SearchFilters.model_json_schema()` в `output_config` API отклонит: в нём нет `additionalProperties: false`.

```python
from app.llm.client import call_structured, load_prompt

def parse_query(query: str) -> SearchFilters:
    return call_structured(
        api_key=settings.anthropic_api_key,
        model=cfg.models["parser"],       # имя модели держите в конфиге, не в коде
        system=load_prompt("parse_query.md"),
        user=query,
        output=SearchFilters,
    )  # обрезанный ответ или отказ → ValidationError / RuntimeError: лог + повтор
```

Точную форму параметров сверяйте с документацией вашей версии SDK: API меняется, а тест на мок-транспорте в `tests/test_llm_client.py` ловит такие расхождения без сети.

**Системный промпт (основа, дальше улучшаете по evals):**

```text
Ты переводишь запросы на поиск недвижимости в Казахстане в фильтры.

Правила:
- Цены в тенге. «40 млн» = 40000000. «до» → price_max_kzt, «от» → price_min_kzt.
- «Евродвушка» = 2 комнаты, «студия» = 1 комната.
- Ставь только то, что сказано явно или однозначно следует из запроса.
  Город по району можно вывести (Есильский район → Астана), угадывать нельзя.
- Всё, что не выражается полями («тихий двор», «для семьи с детьми»), пиши в semantic_query.
- Метро есть только в Алматы. Метро в Астане → needs_clarification.
- Запрос не про недвижимость или слишком размыт → needs_clarification.

Примеры:
«евродвушка в Алматы до 40 млн с ремонтом у метро» →
  city=Алматы, rooms=[2], price_max_kzt=40000000, conditions=[renovated], features=[near_metro]
«аренда 1-комнатной в Есильском районе до 300 тыс» →
  deal_type=rent, city=Астана, districts=[Есильский], rooms=[1], price_max_kzt=300000
«3 комнаты для семьи с детьми, рядом школа, под ипотеку» →
  rooms=[3], features=[near_school, mortgage], semantic_query=«для семьи с детьми»
```

Примеры в промпте и тестовые запросы для evals должны быть разными, иначе метрика будет завышена.

## Поиск, реранкинг и ответ

**Гибридный поиск одним SQL-запросом.** Жёсткие фильтры (город, цена, комнаты) сужают выборку, затем два ранжирования (векторное и полнотекстовое) сливаются через Reciprocal Rank Fusion. `WHERE` собираете в Python из `SearchFilters`, только через параметры, без склейки строк.

```sql
WITH base AS (
  SELECT id, tsv, embedding FROM listings
  WHERE {where_from_filters}
),
vec AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> %(qvec)s) AS r
  FROM base ORDER BY embedding <=> %(qvec)s LIMIT 50
),
fts AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) AS r
  FROM base, websearch_to_tsquery('russian', %(qtext)s) AS q
  WHERE tsv @@ q
  ORDER BY ts_rank_cd(tsv, q) DESC LIMIT 50
)
SELECT id, SUM(1.0 / (60 + r)) AS rrf_score
FROM (SELECT * FROM vec UNION ALL SELECT * FROM fts) AS u
GROUP BY id
ORDER BY rrf_score DESC
LIMIT 50;
```

Тонкости, о которых спрашивают на интервью:

- `qvec` — эмбеддинг `semantic_query`, а если он пустой, то исходного запроса. `qtext` — тот же текст для полнотекстового поиска.
- `ts_rank_cd` в Postgres только приближение к BM25. Для v1 этого достаточно; настоящий BM25 даёт, например, расширение ParadeDB `pg_search`.
- HNSW-индекс с жёсткими фильтрами может вернуть меньше 50 строк. В pgvector 0.8+ это решает `SET hnsw.iterative_scan = relaxed_order`. На 2–3 тыс. строк точный перебор без индекса тоже быстрый: замерьте оба варианта.
- **Ничего не нашлось** — ослабляйте мягкие фильтры по очереди (features → conditions → districts) и честно говорите пользователю, что именно ослаблено.

**Реранкинг.** Сначала замерьте качество без него, потом добавьте и сравните. Варианты: открытая многоязычная модель `bge-reranker-v2-m3` (локально), API-реранкер (Voyage или Cohere) или дешёвая LLM, которая оценивает топ-20 по шкале 0–3. Из 50 кандидатов оставляете 10.

**Ответ.** Передайте модели топ-10 как структурированный список с `id` и требованиями:

- рекомендуй только объекты из списка и ссылайся на них как \[id\];
- коротко объясни соответствие запросу и честно назови расхождения («ремонт есть, но до метро 15 минут»);
- если подходящих нет, так и скажи и предложи, какой фильтр ослабить.

Ответ стримится. Проверка после генерации: все \[id\] в ответе должны быть из переданного списка, это ваша первая защита от галлюцинаций.

**v2: tool use.** Тот же поиск становится инструментом `search_listings` со схемой `SearchFilters`. Модель сама решает, звать ли поиск, уточнить запрос или повторить с другими фильтрами. Ограничьте цикл тремя вызовами инструмента.

## Данные, адаптеры и развёртывание

Один код работает в двух местах: в проде на данных компании и в публичном демо на синтетике. Разница только в адаптере данных и конфиге.

&#91;embedded content: развёртывание · прод и демо на одном коде\]

### Нужен ли отдельный сервер

Да, AI-поиск стоит сделать отдельным сервисом (свой контейнер), а не встраивать в основной бэкенд. Но отдельный сервис не значит отдельная железка: в проде он живёт в той же инфраструктуре компании, рядом с остальными сервисами.

- **Изоляция сбоев.** Вызовы LLM длятся секунды и иногда падают по таймауту. Пусть это замедляет чат, а не основной сайт.
- **Независимый деплой и масштабирование.** Промпты и модели меняются часто, и это не должно требовать релиза всего продукта.
- **Ключи ИИ в одном месте.** Их знает только этот сервис.
- **Один и тот же код для демо и прода.** Разные только конфиг и адаптер.

Свой индекс поиска (отдельная БД или хотя бы отдельная схема в Postgres) нужен по той же причине: тяжёлые векторные запросы не нагружают основную базу, а сервис только читает объявления и ничего в них не пишет. Демо разворачивается отдельно на дешёвом VPS или PaaS и никак не связано с продом.

### Адаптер данных

Ядро работает только с нормализованной моделью объекта (таблица `listings` выше). Адаптер знает, как взять объекты из конкретного источника и привести к этой модели.

```python
class ListingSource(Protocol):
    def fetch_changed(self, since: datetime) -> Iterable[Listing]: ...  # новые и изменённые
    def fetch_removed(self, since: datetime) -> Iterable[str]: ...      # id проданных и снятых
```

Расхождения полей и словари вынесены в конфиг, поэтому подключение новой базы требует минимума кода. Из этого же конфига собираются список признаков в `SearchFilters` и часть промпта разбора.

```yaml
# config/demo.yaml (в репозитории); config/prod.yaml только у компании
source: synthetic_jsonl          # в проде: company_db
cities: [Алматы, Астана]
field_map:                       # поле источника → поле listings
  price: price_kzt
  room_count: rooms
  text: description
features:
  near_metro: «рядом метро»
  parking: «паркинг»
  mortgage: «подходит под ипотеку»
limits:
  daily_budget_usd: 2            # для публичного демо
  requests_per_minute_per_ip: 10
```

**Синхронизация в проде.** Для начала хватит задачи по расписанию раз в 5–15 минут: забрать изменённые по `updated_at`, пересчитать эмбеддинги только там, где изменился текст, и удалить снятые. Позже можно перейти на события из основного бэкенда. Дополнительная страховка: перед показом результата проверять статус объекта, чтобы чат не предлагал проданные квартиры.

### Интерфейс: одна страница чата, два режима

- **Целиком:** страница `/chat` открывается сама по себе: это демо в портфолио и раздел в вашем интерфейсе.
- **Виджет:** сайт подключает одну строку `<script src="https://…/widget.js" data-site-key="pub_…"></script>`. Скрипт рисует кнопку, а по клику открывает popup с iframe той же страницы `/chat?embed=1`. Iframe изолирует стили и скрипты в обе стороны. Клик по объекту в чате передаёт родительской странице событие через `postMessage`, и сайт сам открывает карточку.

### Безопасность

- Ключи LLM и эмбеддингов только в переменных окружения на сервере; в репозитории только `.env.example`.
- `site-key` публичный, это не секрет. За ним на сервере закреплены разрешённые домены (проверка `Origin`, CORS, `frame-ancestors` в CSP) и лимиты запросов.
- Лимиты на IP и дневной бюджет: при его исчерпании демо честно говорит «лимит на сегодня исчерпан».
- В `query_log` не пишем персональные данные посетителей сайта, для прода задайте срок хранения логов.
  - **Что пишется сейчас (демо):** текст запроса, распознанные фильтры, выдача (`source_id`), модель ответа, срабатывание фолбэка, этапы задержки и стоимость. IP, cookies, `site-key` и идентификаторы пользователя не пишутся; текст ответа тоже — он восстанавливается по выдаче и не нужен для метрик.
  - **Маскирование в проде.** Люди вписывают в запрос телефоны, email, имена, номера документов («перезвоните на +7 701…»). Перед записью текст запроса прогоняется через маскирование: телефоны, email, ИИН (12 цифр) и номера карт заменяются на `[телефон]`, `[email]` и т. п.; сырой текст в лог не попадает. Фильтры и выдача ПДн не содержат.
  - **Срок хранения в проде:** 30–90 дней по решению компании — ежедневная задача удаляет старые строки (или партиции по месяцам, удаляемые целиком). Агрегаты для метрик (p50/p95, цена, доля фолбэков) считаются раньше и хранятся без текста запросов.
  - **Доступ:** чтение `query_log` — только у команды поиска; выгрузки для evals — после маскирования.

**До публикации кода** договоритесь с руководителем, лучше письменно: код, написанный в рабочее время или для работы, по умолчанию может принадлежать компании. Рабочая схема: ядро вы публикуете как свой open source проект (например, под лицензией MIT), а компания использует его со своим адаптером.

## Evals

Evals проверяют два слоя по отдельности, иначе непонятно, что сломалось: модель неверно поняла запрос или поиск плохо нашёл.

**Набор из 30 запросов (`evals/cases.jsonl`):**

- 10 простых («2-комнатная в Астане до 30 млн»);
- 10 сложных: сленг, опечатки, несколько условий сразу;
- 5 смысловых, где важен текст описания («тихий двор», «вид на горы»);
- 5 пограничных: метро в Астане, запрос не про недвижимость, невозможная цена. Ожидается `needs_clarification`.

```json
{"id": "q07", "query": "евродвушка в Алматы до 40 млн с ремонтом у метро",
 "expected_filters": {"city": "Алматы", "rooms": [2], "price_max_kzt": 40000000,
                      "conditions": ["renovated"], "features": ["near_metro"]},
 "relevant_ids": [123, 456, 789],
 "tags": ["slang", "metro"]}
```

**Откуда взять `relevant_ids`.** Для синтетики при генерации «подложите» под каждый запрос 2–5 подходящих объектов. Для реальных данных: прогоните широкий поиск и вручную отметьте подходящие среди первых 30. Ручная разметка 30 запросов займёт один вечер, и это самая ценная часть проекта.

| Слой | Метрика | Как считать |
| --- | --- | --- |
| Разбор | точность по полям и % полностью верных | сравнить `SearchFilters` с `expected_filters` |
| Поиск | Recall@10, MRR | доля `relevant_ids` в топ-10; позиция первого верного |
| Ответ | % ответов без чужих \[id\] | автоматически; качество объяснений пока читаете глазами 10 ответов |
| Эксплуатация | задержка p50 и p95, стоимость запроса | из `query_log` |

```python
for case in load_cases("evals/cases.jsonl"):
    filters = parse_query(case.query)
    parse_scores.append(compare_filters(filters, case.expected_filters))
    ids = search(filters, case.query, config=cfg)[:10]
    recall.append(len(set(ids) & set(case.relevant_ids)) / len(case.relevant_ids))
    mrr.append(next((1 / (i + 1) for i, x in enumerate(ids) if x in case.relevant_ids), 0))
save_report(cfg, parse_scores, recall, mrr)  # с датой и версией промпта
```

## План работ

Порядок важен: evals появляются на втором шаге, а не в конце. Тогда каждое следующее улучшение сразу видно в цифрах.

Что сломалось, почему, что исправили и цифры до/после по каждому шагу — в [decisions.md](decisions.md).

- [x] **Шаг 1. Каркас и данные.** Репозиторий, `docker-compose` с Postgres + pgvector, схема БД, протокол `ListingSource` и демо-адаптер, генерация 2–3 тыс. синтетических объектов, `sync_index.py`.
  *Сделано: 1000 синтетических объектов (догенерировать до 2–3 тыс. — `--count`), у всех эмбеддинги.*
- [x] **Шаг 2. Разбор запроса и evals-разбора.** `SearchFilters`, промпт, `POST /parse`, 30 кейсов в `cases.jsonl` с ожидаемыми фильтрами. Цель: не меньше 90% полностью верных.
  *Сделано: dev (20) 100% ± 0%, holdout (10) 97% ± 6% полностью верных, ×3 — [decisions.md](decisions.md#разбор-запроса).*
- [x] **Шаг 3. Поиск.** Сначала только векторы, замер Recall@10. Затем гибрид с RRF, ослабление фильтров, снова замер. Размечаете `relevant_ids`.
  *Сделано: dev, группа «ранжирование решает» (12 кейсов) — векторы Recall@10 47% / MRR 0,70, гибрид 62% / 0,79; ослабление фильтров — набор `relax` 6/6. Разметка: авто для кейсов без смысла, LLM + ручная проверка для смысловых, дооценка по пулу. Holdout без смысловых кейсов с подходящими — вывод только по dev. [decisions.md](decisions.md#поиск).*
- [ ] **Шаг 4. Реранкинг и ответ.** Реранкер, генерация ответа со ссылками \[id\], проверка id, стриминг, `query_log`.
- [ ] **Шаг 5. Интерфейс и демо.** Страница чата, `widget.js` с popup и iframe, лимиты и site-key, деплой демо на отдельный дешёвый сервер.
- [ ] **Шаг 6. v2 и упаковка.** Режим tool use, сравнение с v1 по evals, README, видео.
- [ ] **Шаг 7. Прод (после согласования с руководителем).** Прод-адаптер к БД компании, `config/prod.yaml`, синхронизация по расписанию, деплой в инфраструктуру компании, виджет на сайте.
  - **Прод — новостройки, а не объявления.** Демо ищет по объявлениям (одна строка = одна квартира с описанием продавца); у компании — жилые комплексы и квартиры в них. Это меняет модель данных и выдачу:
    - **Модель «ЖК → квартиры».** У ЖК — застройщик, адрес, класс, срок сдачи, инфраструктура, описание; у квартиры — планировка, комнаты, площадь, этаж, цена, статус (свободна / бронь / продана).
    - **Смысловой текст — на уровне ЖК.** «Тихий двор», «вид на горы», «рядом школа» описывают комплекс, а не отдельную квартиру: `search_text` и эмбеддинги строятся по ЖК, жёсткие фильтры (цена, комнаты, площадь, этаж) — по квартирам. Поиск находит ЖК по смыслу и квартиры в них по фильтрам.
    - **Группировка выдачи по ЖК и планировке:** вместо десяти одинаковых квартир одного дома — «ЖК X: 2-комнатные 58–64 м², 41–47 млн, 12 свободных».
    - **Новые фильтры:** срок сдачи (квартал / год, «уже сдан»), класс жилья (эконом / комфорт / бизнес / премиум), этаж (не первый / не последний / диапазон), способы покупки (ипотека, рассрочка, программы).
    - **Сценарий с заявкой.** Цель — не только ответ, но и контакт: «записаться на просмотр / получить планировки» → заявка в CRM компании (с согласием на обработку ПДн; в `query_log` контакты не попадают).
  - **Где что живёт.** Общие для любой базы новостроек вещи (двухуровневая модель, группировка, новые типы фильтров, событие «заявка» с подключаемым обработчиком) — в ядре, включаются конфигом. Специфика компании (адаптер к её БД, словари классов и программ, интеграция с конкретной CRM, `config/prod.yaml`) — в приватном репозитории.
